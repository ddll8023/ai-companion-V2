# AI Companion — 开发进度文档

> 本文档用于规划 AI Companion 的**开发阶段、阶段顺序、依赖关系和交付标准**。
>
> 本文档面向开发人员，是模块说明文档（业务视角）与实际编码之间的桥梁。
>
> 本文档只描述"按什么顺序开发什么东西、怎么验证"，不描述具体类、函数、接口路径或实现代码。

---

## 1. 总体开发策略

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| **垂直切片优先** | 按业务闭环逐轮推进，每轮交付可验证功能 |
| **分层递进** | 每一轮以内先架构后功能，从底层向上构建 |
| **最小桌面运行时提前** | 前后端基础完成后立即建立 Electron、Python 本地服务和前端之间的真实运行链路。浏览器模式只作为开发辅助环境，不作为正式产品架构 |
| **增量扩展** | 数据库模型、API、Service 只写到当前轮次够用为止，后续按需扩展 |
| **核心闭环连续开发** | 对话→记忆提取→检索使用连续完成，不切成两段 |
| **跨平台公共能力优先** | macOS 和 Windows 的具体系统适配之前，先建立统一的平台能力、权限状态、采集事件和隐私规则模型。平台差异只能存在于 Electron 平台适配层 |
| **数据生命周期同步建设** | 每个业务模块在创建数据能力时同步定义删除、关联清理、迁移和基础审计，不允许只实现创建和查询后再集中补数据治理 |

### 1.2 技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| 桌面壳 | Electron + electron-builder | 打包、窗口、托盘、进程管理、IPC |
| 前端 | Vue 3 + TypeScript + Pinia + Vue Router + Axios | Composition API + `<script setup>` |
| 样式 | Tailwind CSS v4 | `@import "tailwindcss"` + `@theme` 指令 |
| 图标 | FontAwesome 6 | 禁止使用 Element Plus 及其他组件库 |
| 后端 | Python + FastAPI + SQLAlchemy | 本地 HTTP 服务 |
| 数据库 | SQLite + FTS5 | WAL 模式 |
| 数据库迁移 | 数据库版本迁移能力 | 从阶段 1 建立，后续每个阶段同步增加迁移 |
| 依赖管理 | uv（后端）/ npm（前端） | — |
| 密钥存储 | macOS Keychain / Windows Credential Manager | 由 Electron 主进程管理 |

### 1.3 通信架构

前端建立统一通信抽象层，不同运行环境使用不同适配器，页面和 Store 不感知通信差异：

- **浏览器开发环境**：通信层使用 HTTP 适配器，直连本地服务
- **Electron 正式环境**：通信层使用桌面桥接适配器，通过 IPC 转发请求
- **环境判断集中在通信层**，不在页面中散落 `window.electronAPI` 判断
- **页面不持有本地服务地址**，不直接构造 HTTP 请求到本地服务

- 阶段 0 必须先完成。
- 阶段 1 和阶段 2 在阶段 0 完成后可并行。单人开发时可以交替推进；多人开发时可以并行推进。
- 阶段 3 需要阶段 1 和阶段 2 都完成后才能开始。
- 阶段 4 到阶段 9 在阶段 3 基础上按顺序推进。
- 阶段 10 在阶段 3 基础上独立开发，与阶段 4—9 属于并行分支。
- 阶段 11 和阶段 12 依赖阶段 10，可并行开发。

## 3. 详细阶段说明

### 阶段 0——项目脚手架与工程基线

**定位**：项目基础框架搭建，确保三端各自可独立启动。

**目标**：创建三个子项目（`backend/`、`frontend/`、`electron/`）的初始工程骨架。

**核心任务**：

| 端 | 任务 | 关键配置 |
|----|------|----------|
| backend | Python 项目结构 `app/` | `pyproject.toml`、`.env`、uv 虚拟环境 |
| frontend | Vite + Vue 3 + TypeScript 项目 | `package.json`、`vite.config.ts`、`tsconfig.json` |
| electron | Electron 主进程 + preload | `package.json`、`tsconfig.json`、`electron-builder.yml` |

**关键设计点**：
- 统一项目基础配置和环境变量约定
- 统一日志目录和数据目录概念（具体路径由 Electron 确定，此处只建立概念）
- 前端规范明确：Vue 3 Composition API、`<script setup>`、TypeScript、Pinia、Vue Router、Axios、Tailwind CSS v4、FontAwesome 6、自定义 Vue 组件；禁止 Element Plus
- 三个子项目可以独立启动
- 本阶段不提前建立全部业务页面和数据库表

**验收方式**：
- `cd backend && uv run uvicorn app.main:app` → 服务启动
- `cd frontend && npm run dev` → Vite 开发服务器启动
- `cd electron && npm run dev` → Electron 窗口弹出

**前置依赖**：无

---

### 阶段 1——后端与数据基础

**定位**：后端服务的基础能力和通用设施，所有上层业务模块的底座。

**目标**：FastAPI 服务能启动，具备完整的统一响应、异常处理、数据库连接、迁移和基础审计能力。

**核心任务**：

| 分类 | 任务 |
|------|------|
| 入口 | `app/main.py`（FastAPI app + CORS + 生命周期事件） |
| 配置 | `app/core/config.py`（Settings + 环境变量）+ `app/core/database.py`（SQLite + SQLAlchemy + get_db） |
| 通用响应 | `app/schemas/common.py`（ApiResponse、ErrorCode、PaginatedResponse） |
| 异常处理 | 全局异常处理器 + `ServiceException` + `commit_or_rollback` |
| 数据库迁移 | 建立数据库版本和迁移能力。新数据库可从空状态初始化，已有数据库可按版本升级。迁移失败时不能继续启动写业务 |
| 基础审计 | 建立基础审计能力和审计数据结构供后续业务模块记录关键事件。不在本阶段建立完整审计页面 |
| 基础运行状态 | 健康检查至少区分：服务运行、数据库可用、数据库迁移完成、数据目录可写。不在健康检查时进行外部模型网络调用 |
| 数据目录 | 浏览器开发模式使用开发配置目录。Electron 正式环境的数据目录由 Electron 主进程确定并传给本地服务。Python 不自行猜测 Electron 用户数据目录 |

**关键设计点**：
- SQLite 使用 WAL 模式
- CORS 允许 Vite 开发服务器端口
- 数据库、导出、备份和日志使用统一数据根目录
- 后续每个阶段新增数据模型时必须同步增加迁移

**验收方式**：
- `curl localhost:PORT/health` 返回正确的运行状态信息
- 数据库文件自动创建
- 数据库版本变更可通过迁移正常升级

**前置依赖**：阶段 0

**可与阶段 2 并行**：是

---

### 阶段 2——前端基础

**定位**：前端应用的基础框架、导航、布局、通用状态管理和统一通信抽象。

**目标**：Vue 3 应用具备完整的路由、布局、Axios 封装、Pinia 状态管理和运行环境适配能力。

**核心任务**：

| 分类 | 任务 |
|------|------|
| 入口 | `src/main.ts` + `App.vue` + 全局样式入口 |
| 路由 | `src/router/index.ts`（路由入口，按需后续逐步添加页面） |
| 布局 | 侧边栏导航 + 主内容区（响应式布局）|
| 统一通信层 | 根据运行环境选择 HTTP 适配器或 Electron 适配器。页面和 Store 使用统一业务接口，不感知通信差异 |
| API 层 | Axios 封装 + 统一错误处理 + 响应解析 |
| 状态管理 | Pinia 实例注册 |
| 基础页面骨架 | 应用布局、导航、路由配置。优先完成路由入口而非数量 |
| 通用组件 | 加载、空数据、错误、权限不足状态组件；统一确认组件 |

**关键设计点**：
- 前端通信层根据运行环境选择适配器，页面和 Store 不判断 `window.electronAPI`
- 页面不持有本地服务地址
- 对外 API 协议统一使用 snake_case。前端 API 类型与后端协议保持一致。组件内部确有必要时由业务适配层转换。不在 Axios 拦截器中无条件递归转换所有数据，避免日期、文件、流式数据和第三方响应被错误转换
- 路由使用懒加载 `() => import(...)`
- 本阶段不提前创建大量空页面逻辑

**验收方式**：
- 浏览器打开 Vite 开发服务器 → 看到应用布局和导航
- 通信层可调用后端 `/health` 接口
- 加载/空数据/错误组件可展示

**前置依赖**：阶段 0

**可与阶段 1 并行**：是

### 阶段 3——最小 Electron 运行时

**定位**：建立正式桌面产品的最小运行链路，确保后续业务从一开始就在真实 Electron 架构中运行。

**目标**：Electron 主进程能启动 Python 本地服务，Renderer 通过受控安全通信访问本地服务，密钥通过操作系统安全存储管理。

**核心任务**：

| 分类 | 任务 |
|------|------|
| 应用单实例 | 确保同一时间只有一个应用实例运行 |
| 主窗口 | 创建和管理主窗口生命周期 |
| Python 进程管理 | 主进程启动和关闭 Python 本地服务（`child_process.spawn`）；健康检查轮询；Python 异常退出状态处理；应用退出时清理本地服务 |
| 数据目录 | Electron 统一确定数据目录路径（如 `userData/data/`），传给本地服务 |
| 安全通信 | Electron 生成并持有本地服务随机端口和认证信息；Preload 提供受控白名单能力；Renderer 通过统一通信接口访问本地服务 |
| 密钥管理 | 操作系统安全存储能力（macOS Keychain / Windows Credential Manager） |
| 运行状态 | 本地服务运行状态查询，在界面展示可用或不可用状态 |

**安全关键设计**：

Renderer（前端）不得获得以下内容：
- Python 本地服务端口
- 本地认证令牌
- 数据库路径
- Python 可执行文件路径
- 模型 API Key
- 数据库密钥

正确职责划分：
- Electron Main 持有端口和认证信息
- Renderer 只调用明确的业务能力
- Main 将请求代理到本地服务
- Preload 不暴露通用的任意 IPC 发送能力
- 本地服务只监听本机回环地址
- 本地服务拒绝没有正确认证信息的请求

**本阶段不要求完成**：
- 完整活动采集
- 完整托盘交互
- 完整数据治理
- 用户画像
- 所有业务页面

**验收方式**：
- Electron 启动后自动启动 Python 本地服务
- Renderer 能通过受控通信调用健康状态，且 Renderer 不知道本地端口和认证信息
- 应用退出后本地服务能正常结束
- 本地服务异常退出时界面能展示不可用状态
- Windows 和 macOS 均能完成最小运行链路验证
- 安全存储能够保存和读取测试密钥

**前置依赖**：阶段 1、阶段 2

### 阶段 4——模型配置

**定位**：用户管理模型供应商、模型列表和密钥的入口，是 AI 对话功能的前提条件。

**目标**：用户可配置至少一种外部模型（OpenAI / Anthropic 兼容），并通过操作系统安全存储保存密钥。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/models/system.py` → `model_configs` 模型定义 |
| 后端 | `app/schemas/model.py` → ModelConfig Request/Response |
| 后端 | `app/services/model_provider.py` → 配置 CRUD + 连接测试 + 模型调用统一接口 |
| 后端 | `app/api/models.py` → 配置路由 |
| 前端 | 模型配置页面：供应商选择、模型名、API Key 输入（通过受控桌面能力保存）、连接测试按钮、激活状态展示 |

**关键设计点**：
- API Key 不写入 SQLite
- API Key 不返回 Renderer
- 页面只能知道"是否已配置"
- 用户输入的新密钥通过受控桌面能力保存到操作系统安全存储
- Python 使用密钥时只在运行时从 Electron 获取
- 日志、错误信息和审计中不得记录完整密钥
- 配置过程需要区分：非敏感配置保存成功、密钥保存成功、连接测试成功、配置已激活、配置存在但当前不可用
- 不能只用一个"已配置"状态覆盖全部结果

**验收方式**：
- 输入 API Key → 测试连接成功 → 状态变为"已配置且可用"
- 输入错误 API Key → 测试连接失败 → 展示明确错误提示
- API Key 不存储在 SQLite

**前置依赖**：阶段 3（Electron 密钥存储能力）

### 阶段 5——基础对话（无记忆）

**定位**：核心对话功能，用户可多会话地与 AI 进行流式对话。

**目标**：创建、切换、删除会话；发送消息并接收流式回复；中断正在生成的回复。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/models/chat.py` → `sessions`、`messages` 模型 |
| 后端 | `app/schemas/chat.py` → 会话/消息 Request/Response |
| 后端 | `app/services/chat.py` → 会话 CRUD、消息保存、流式回复编排 |
| 后端 | `app/api/chat.py` → 对话路由（含 SSE 流式输出） |
| 前端 | 对话页面：会话列表 + 消息区域 + 输入框 + 流式渲染 + 停止生成按钮 |

**流式持久化设计**（非逐片段写入）：
```
用户消息 → 先持久化到数据库
创建助手占位消息 → 标记为"生成中"
模型流式内容 → 主要在内存中累积并推送前端
  必要时可保存阶段性检查点，但不得逐片段提交数据库
正常完成 → 一次性保存完整回复
用户中止 → 保存已生成的有效内容，标记为"已中止"
模型失败 → 保存失败状态和必要错误信息
助手消息最终必须进入"完成"、"已中止"或"失败"状态，不能长期停留在"生成中"
```

**并发规则**：
- 同一会话同一时间只允许一个生成任务
- 用户切换到其他会话不应自动中止当前会话
- 用户在同一会话再次发送消息前，需要结束或中止当前生成
- 新生成不得静默覆盖旧生成
- 每个会话的生成状态独立管理
- 应用退出或本地服务异常时，生成中的消息需要收敛到明确状态

**自动标题降级**：
- 会话创建时先使用默认标题或用户消息摘要
- AI 标题生成作为非阻塞派生操作
- 标题生成失败不影响会话和对话

**验收方式**：
- 新建会话 → 输入消息 → 流式回复逐段出现 → 回复完整
- 切换会话 → 历史消息正确显示
- 中断回复 → 回复停止，已写内容保存
- 删除会话 → 会话消失

**前置依赖**：阶段 4（模型配置）

### 阶段 6——后台任务

**定位**：处理不应阻塞用户主流程的异步派生工作，包括记忆提取、画像刷新、数据清理等。

**目标**：创建、领取、执行、追踪后台任务，任务状态收敛到最终状态。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/models/task.py` → `background_tasks` 模型（含 dedup_key、source_version、优先级、重试机制） |
| 后端 | `app/schemas/task.py` → 任务请求/响应 Schema |
| 后端 | `app/services/task.py` → 任务 CRUD + 排他领取 + 去重 + 超时恢复 + 重试逻辑 |
| 后端 | `app/tasks/registry.py` → 任务处理器注册表（`@register_handler` 装饰器） |
| 后端 | `app/tasks/executor.py` → 任务执行器（查找处理器、解析参数、更新状态） |
| 后端 | `app/tasks/scheduler.py` → 简单轮询调度器（独立线程，定时查询待处理任务并执行） |
| 后端 | `app/api/tasks.py` → 任务 API 路由（创建/查询/取消/积压统计） |

**关键设计点**：
- 使用 SQLite 任务表实现，不引入外部消息队列
- 调度器定时轮询检查待处理任务
- 任务领取必须具备排他性，避免同一任务被重复执行
- 任务参数不能仅依靠无序对象直接判断重复；不同任务类型需要定义自己的去重依据
- 任务执行需要记录来源内容版本；来源内容已经修改或删除时，旧任务不得继续写回结果
- 应用重启后，未完成任务可以恢复
- 执行中的任务超时后进入待重试，不直接创建一个新的重复任务
- 单个任务异常不能导致整个调度器停止
- 后台任务必须具有最终状态
- 对话完成后创建记忆提取任务时，需要保证消息保存和任务创建的一致性

**任务状态流转**：
```
待处理 → 执行中 → 已完成
   ↓        ↓
 待重试 → 已失败
   ↓
 已取消
```

**验收方式**：
- 创建任务 → 调度器领取 → 执行完成 → 状态变为已完成
- 创建失败任务 → 自动重试 → 重试耗尽 → 状态变为已失败
- 重复任务 → 按业务定义去重，不重复创建

**前置依赖**：阶段 1、阶段 5

### 阶段 7——记忆提取与审查

**定位**：从对话内容中识别重要信息，生成候选记忆，供用户审查确认。

**目标**：对话完成后自动提取候选记忆，用户可确认、纠正、否定、删除记忆，查看来源和修订历史。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/models/memory.py` → `memories`、`memory_sources`、`memory_revisions` 模型 |
| 后端 | `app/schemas/memory.py` → 记忆 Request/Response |
| 后端 | `app/tasks/registry.py` → 任务处理器注册表（`@register_handler("memory.extract")`） |
| 后端 | `app/tasks/memory_extract.py` → 记忆提取后台任务 |
| 后端 | `app/services/memory.py` → 记忆 CRUD + 审查操作 + 状态管理 |
| 后端 | `app/api/memories.py` → 记忆路由 |
| 前端 | 长期记忆页面：按状态筛选、记忆卡片（含来源证据）、确认/纠正/否定/删除操作、修订历史 |

**版本控制**：
- 候选记忆生成时需要关联来源内容版本
- 如果来源消息在任务执行前被删除或修改，不得继续生成旧记忆，不得将旧任务结果写入当前状态

**去重与合并**：
- 识别完全重复记忆
- 识别高度相似记忆
- 避免同一次对话重复生成相同候选
- 对可能冲突的记忆保留来源，不自动覆盖用户已确认内容

**删除语义区分**：
- **用户否定**：保留否定状态，用于防止系统再次使用同一错误记忆
- **用户删除**：进入领域删除流程，清理记忆正文、来源、修订数据、引用关系和索引
- 审计仅保留不含记忆正文的必要元信息
- 如业务需要短期保留删除标识，只能保留不包含敏感正文的墓碑信息

**记忆状态流转**：
```
模型生成候选 → 候选（candidate）
  ├─ 用户确认 → 已确认（confirmed）→ 进入索引
  ├─ 用户纠正 → 已纠正（corrected）→ 进入索引
  ├─ 用户否定 → 已否定（rejected）→ 不进索引，保留否定标识
  └─ 用户删除 → 已删除（deleted）→ 领域删除
```

**验证方式**：
- 完成对话 → 后台生成候选记忆 → 记忆页面可见
- 确认记忆 → 状态变为已确认
- 纠正记忆 → 新内容替换旧内容，旧版本进入修订历史
- 否定记忆 → 不再出现
- 删除记忆 → 关联数据清理

**前置依赖**：阶段 5（对话）、阶段 6（后台任务）

### 阶段 8——记忆检索与个性化上下文

**定位**：在对话时检索已确认记忆，组装为上下文传递给 AI，实现个性化对话。

**目标**：基于用户消息，从有效记忆中检索最相关的内容，带入对话上下文中。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/services/retrieval.py` → 多信号检索（FTS5 全文 + 时间新鲜度 + 重要性 + 状态过滤 + 去重） |
| 后端 | `app/services/embedding.py` → 嵌入向量生成服务（FastEmbed + ONNX Runtime，默认模型 bge-small-zh-v1.5，512 维） |
| 后端 | `app/services/retrieval.py` → 向量语义检索分支：余弦相似度 Top 20 + FTS5 Top 20 + RRF 融合排序 |
| 后端 | 记忆状态变化（确认/纠正/删除）时同步更新向量索引（BLOB 存储，NumPy 加载检索） |
| 后端 | 上下文组装 → 根据模型容量动态计算记忆预算 |
| 后端 | 对话流程增强 → 发送消息时先检索记忆再构造 Prompt |

**关键设计点**：
- 默认嵌入模型 bge-small-zh-v1.5，FastEmbed + ONNX Runtime CPU 完全本地离线推理，无需 GPU，无需联网
- 嵌入向量以 BLOB 直接存入 memories 表对应行（新增 embedding 列），依赖 numpy 加载后做余弦相似度计算
- 混合检索采用 FTS5 Top 20 + Vector Top 20 → Reciprocal Rank Fusion（RRF）融合排序，与现有的时间新鲜度、重要性信号叠加
- 保留 FTS5 和中文 LIKE 降级，向量不可用时退回到原有全文检索分支，不阻塞对话
- 只检索状态为「已确认」和「已纠正」的记忆
- 上下文长度根据模型上下文容量、系统提示词、近期消息和输出预留动态计算记忆预算
- 设置最大记忆条数和最大上下文长度上限
- 遵循最小必要上下文原则。具体比例属于配置策略，不在进度规划中写死
- 检索结果带回来源信息和相关度
- 对话生成前记录候选检索结果，对话完成后保存实际使用的记忆引用列表
- 被删除、否定或失效的记忆不得进入后续上下文
- 检索失败不能伪装成"没有记忆"
- FTS5 不可用时保留基础对话，并展示个性化能力受限

**验证方式**：
- 会话中有已确认的记忆 → 新对话中提及相关内容 → AI 回复使用了该记忆
- 被否定的记忆不会被检索到
- 记忆检索失败 → 对话仍可用，提示个性化暂时受限

**前置依赖**：阶段 7（必须有已确认记忆）

### 阶段 9——目标与任务

**定位**：将 AI 理解和用户意图转化为可追踪的目标和任务。

**目标**：用户可创建管理目标，AI 可从对话中建议任务，用户确认后才创建。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/models/goal.py` → `goals`、`tasks` 模型 |
| 后端 | `app/services/goal.py` → 目标 CRUD + 任务 CRUD + AI 建议生成 |
| 后端 | `app/api/goals.py` → 目标任务路由 |
| 前端 | 目标任务页面：目标列表（含进度）、任务列表（含优先级）、创建/修改/删除、AI 建议确认面板 |

**关键设计点**：
- AI 生成的内容是建议，不是正式任务。用户确认后才能创建正式任务
- AI 建议被拒绝后不得继续作为正式任务引用
- 删除目标时必须明确关联任务的处理方式（级联删除或解除关联）
- 对话引用目标任务时只读取有效状态
- 创建、更新、删除和确认 AI 建议需要记录基础审计

**目标任务安排在活动采集之前的原因**：
- 目标任务直接增强对话闭环
- 不依赖操作系统高权限能力
- 开发和验证风险低于桌面采集
- 可以较早形成"理解到行动"的产品价值

**验证方式**：
- 创建目标 → 目标出现在列表中
- 关联任务 → 任务显示进度
- 对话中表达意图 → AI 建议任务 → 用户确认 → 出现在任务列表
- 拒绝 AI 建议 → 不会出现在任务列表中

**前置依赖**：阶段 5（对话中 AI 建议）

### 阶段 10——跨平台活动采集基座

**定位**：在 macOS 和 Windows 具体适配之前，建立共用的活动采集、权限、隐私和数据协议。

**目标**：Windows 和 macOS 共用的活动采集框架，包括统一的事件格式、隐私规则、后端处理和前端页面。

**核心任务**：

| 端 | 任务 |
|----|------|
| Electron | 统一平台能力描述接口；统一权限状态枚举 |
| 后端 | `app/models/activity.py` → `activities`、`privacy_rules` 模型（含基础删除和审计） |
| 后端 | `app/schemas/activity.py` → 活动/规则 Request/Response |
| 后端 | `app/services/activity.py` → 活动二次校验、去重、脱敏、批量提交、隐私规则引擎 |
| 后端 | `app/api/activities.py` → 活动/规则路由 |
| 前端 | 活动记录页面公共部分 + 隐私设置页面公共部分 |
| 前端 | 平台能力状态展示 |

**权限状态**：至少区分可用、待授权、已拒绝、受系统限制、当前平台不支持、产品暂未实现。不得将未授权、不支持、未实现和无数据混为同一状态。

**统一活动事件格式**：应用名称、窗口标题、开始时间、结束时间、持续时长、用户空闲状态、采集来源平台、隐私规则处理结果。

**隐私双层防护**：

**Electron 层**（采集前硬阻断）：
- 全局暂停
- 明确应用黑名单
- 无法识别前台应用时停止采集
- 权限异常时停止采集
- 系统安全场景阻断
- 已知高敏感应用阻断

**Python 层**（入库前二次处理）：
- 事件格式校验
- 去重
- 时间范围校验
- 规则状态校验
- 必要脱敏
- 无效或异常事件拒绝
- 只保存处理后的内容

**失败关闭**：当系统不能确定当前场景是否可以采集时，应停止采集，而不是默认允许。

**活动数据删除**：活动数据模型建立时同步实现单条删除、时间范围删除、来源关联清理、行为统计失效处理和基础审计。

**验证方式**：
- 后端 API 可用
- 前端活动设置页面可用
- 统一的隐私规则模型可创建、修改和查询

**前置依赖**：阶段 3（Electron 运行时）

### 阶段 11——macOS 活动采集适配

**定位**：macOS 平台的具体桌面活动采集适配。

**目标**：macOS 平台上，用户授权后能获取前台应用、窗口标题和空闲状态，转换为统一活动事件。

**核心任务**：
- 获取前台应用（NSWorkspace / Accessibility API）
- 在权限允许时获取窗口标题
- 获取用户空闲状态（AGIdleTime）
- 检测相关系统权限，引导用户处理未授权状态
- 将 macOS 原始状态转换为统一活动事件
- 将平台错误转换为统一能力状态

**隐私处理说明**：
- 窗口标题只能作为辅助规则，不能可靠识别应用内部密码框
- 产品不能承诺仅凭窗口标题识别全部敏感内容
- 高敏感应用优先使用应用级阻断
- 无法确认安全时停止采集

**本阶段不重复实现**：活动数据表定义、隐私规则后端、完整前端页面（这些已在阶段 10 完成）。

**验证方式**：
- 开启采集 → 打开几个应用 → 活动记录出现在页面
- 将某个应用加入黑名单 → 该应用不再被记录
- 暂停采集 → 停止记录
- 状态展示反映真实的权限状态

**前置依赖**：阶段 10

### 阶段 12——Windows 活动采集适配

**定位**：Windows 平台的具体桌面活动采集适配。

**目标**：Windows 平台上实现与 macOS 相同的活动采集能力，使用一致的协议和页面。

**核心任务**：
- 获取前台窗口和应用（GetForegroundWindow + GetWindowText）
- 获取窗口标题
- 获取用户空闲状态（GetLastInputInfo）
- 处理平台权限和系统异常
- 转换为统一活动事件
- 输出统一能力状态

**关键设计点**：
- Windows 和 macOS 共享后端数据结构和前端页面
- 差异仅保留在 Electron 平台适配层
- 不在业务 Service 中散落平台判断
- 不因 Windows 权限模型不同而改变业务协议

**验证方式**：同阶段 11，在 Windows 上测试

**前置依赖**：阶段 10

### 阶段 13——用户画像与行为理解

**定位**：从已确认记忆和时间窗口统计中形成可审查的用户理解。

**目标**：展示用户画像特征及其证据来源、行为模式和活动趋势。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/models/profile.py` → `profiles`、`profile_sources` 模型 |
| 后端 | `app/services/profile.py` → 画像生成（后台任务）、画像 CRUD |
| 后端 | 行为统计 → 活跃时段、应用使用分布、对话活跃度 |
| 后端 | `app/api/profiles.py` → 画像路由 |
| 前端 | 用户理解页面：画像特征 + 证据来源 + 置信度 + 修订历史 + 行为模式统计 |

**关键设计点**：
- 画像是派生理解，不能替代原始记忆和活动记录
- 画像生成任务必须关联来源记忆版本
- 用户已经纠正的画像不得被自动刷新直接覆盖
- 长期画像与时间窗口行为统计分开存储
- 删除来源记忆后需要重新评估相关画像
- 行为统计失败不影响长期记忆和对话
- 画像删除和修订需要记录基础审计
- 置信度不能替代用户确认

**验证方式**：
- 有多条记忆和活动记录 → 画像页面展示特征和统计
- 用户纠正画像特征 → 更新生效，旧版本进入修订历史
- 删除相关记忆 → 画像特征受影响

**前置依赖**：阶段 8（有效记忆）、阶段 11（macOS 活动）、阶段 12（Windows 活动）

### 阶段 14——完整数据治理

**定位**：管理本地数据从产生、审查、保留到删除、导出、备份和恢复的完整生命周期。前面的业务阶段已同步建设基础删除和审计，本阶段负责完整治理能力。

**目标**：用户可以导出数据、配置保留策略、创建恢复备份、清除全部数据。

**核心任务**：

| 端 | 任务 |
|----|------|
| 后端 | `app/services/data_governance.py` → 跨模块统一级联删除、数据导出、备份恢复、保留策略、清除全部数据 |
| 后端 | `app/api/data.py` → 数据治理路由 |
| 前端 | 数据管理页面：保留策略配置、导出（时间/范围/状态）、备份创建和恢复、清除全部数据（二次确认） |

**删除操作必须处理**：
- 原始数据
- 来源证据
- 修订历史
- 画像派生
- 对话引用
- 全文索引
- 后续可能存在的向量索引
- 行为统计
- 后台待处理任务
- 不含正文的审计元信息

**恢复要求**：

- 恢复失败时恢复原数据库，不得留下部分恢复状态

**验证方式**：
- 删除一条记忆 → 相关引用和索引被清理
- 导出数据 → 文件生成，内容可读
- 创建备份 → 恢复 → 数据完整
- 清除全部数据 → 所有表清空，索引重建

**前置依赖**：阶段 5（对话）、阶段 7（记忆）、阶段 9（目标任务）、阶段 11/12（活动数据）、阶段 13（用户画像）

## 5. 关键风险与应对

| 风险 | 影响阶段 | 应对方向 |
|------|----------|----------|
| Electron 与 Python 生命周期不一致 | 阶段 3、5、6 | 主进程统一管理状态，异常退出后任务和消息收敛 |
| Renderer 获得过多权限 | 阶段 3 | Preload 白名单，隐藏端口、令牌、路径和密钥 |
| 数据库迁移失败 | 阶段 1 及后续 | 从阶段 1 建立版本迁移，迁移失败禁止继续写入 |
| 流式回复频繁写 SQLite | 阶段 5 | 内存累积，完成或中止时持久化，必要时检查点保存 |
| 同一会话并发生成 | 阶段 5 | 会话级生成状态，同一会话只允许一个活动生成 |
| 后台任务重复执行 | 阶段 6—14 | 排他领取、业务去重键、来源版本校验 |
| 模型结构化输出不稳定 | 阶段 7、13 | Schema 和业务规则校验，模型结果只作为候选 |
| 隐私规则无法识别应用内部敏感区域 | 阶段 10—12 | 应用级阻断、失败关闭、窗口标题仅作辅助 |
| macOS 权限被拒绝或撤销 | 阶段 11 | 独立权限状态和降级路径 |
| Windows/macOS 能力差异扩大 | 阶段 10—12 | 统一平台接口和能力状态，业务层不判断平台 |
| SQLite 并发写入竞争 | 阶段 5、6、10—14 | WAL 模式、短事务、批量活动提交、减少流式写入 |
| 删除原始数据后派生数据残留 | 各业务阶段、阶段 14 | 业务阶段同步删除，阶段 14 完成统一级联治理 |
| 用户修订被自动任务覆盖 | 阶段 7、13 | 用户修订优先，自动任务写入前校验版本和状态 |
